# GUI Gap Analysis — Mission Control Upgrade

**Date:** 2026-06-16
**Scope:** `OpenGoal` (plugin) + `opencode-source` (desktop app) crossover
**Method:** Spec-to-implementation walk, line-by-line `MISSION_CONTROL_UI_DESIGN.md` mapping against source + test coverage
**Test baseline:** 1,721 tests (1,157 plugin + 552 app + 12 desktop), all green, typecheck clean on both packages, desktop build succeeds

---

## How to read this

Each gap is a spec requirement that has **no implementation**, **incomplete implementation**, or **no test coverage**. Gaps are not bugs — the code does what it's written to do. Gaps are things the code was never written to do in the first place, or things the test suite cannot verify by construction.

"Testable?" means: could a failing test be written today that turns red when this gap is filled?

## Gap 1 — RenderBlock Protocol: Plugin Ships, App Never Consumes

**Severity:** Architectural
**Surface:** App ↔ Plugin crossover
**Testable?** Yes — would need a new app-side BlockRenderer component

The plugin has a full `RenderBlock` type system across 5 files:

| File | Role |
|---|---|
| `src/blocks/types.ts` | `RenderBlock` discriminated union, `RenderBlocksMetadata`, diff types |
| `src/blocks/factories.ts` | Factory functions with autogenerated keys |
| `src/blocks/goal-blocks.ts` | Goal-state → `RenderBlock[]` mapping |
| `src/blocks/to-text.ts` | `blockToText()` / `blockToTextForLLM()` (plaintext + LLM variants) |
| `src/blocks/validate.ts` | `validateBlocks()` with filtered output + error reporting |

`src/server.ts:67-81` calls `ctx.metadata({ metadata: { blocks } })` — with this comment:

```
// context.metadata() is the vNext path for RenderBlock emission
// (specs/render-protocol-design.md). It may not be present in older
// SDK versions or test harnesses — guard with a runtime check.
//
// Returns a plain-text fallback rendering of the blocks so they are
// always visible in the conversation, even when the Desktop
// BlockRenderer is not yet wired up.
```

The app side has **zero references** to `RenderBlock`, `ctx.render`, or `render-protocol` anywhere in `packages/app/src/`. Instead, `goal-panel.tsx` polls `.opencode/.goal-state.json` every 2 seconds via `sdk.client.file.read()`.

**Impact:** The spec's render protocol pipeline (plugin emits `RenderBlock[]` → app renders Slack-Block-Kit-style cards) is implemented on the producer side but abandoned at the consumer. The dock is a file-poller, not a block renderer. The plugin's `RenderBlock` infrastructure is essentially dead code from the app's perspective — the plaintext fallback in the conversation is the only consumer.

## Gap 2 — "Stalled" Run State: Absent

**Severity:** Feature gap
**Surface:** Both repos
**Testable?** Yes

The spec lists six run states (line 77):

> current run state: active, paused, achieved, stalled, stopped

The lifecycle model (`goal-panel-lifecycle.ts`) handles exactly four:

| Spec State | Implemented? |
|---|---|
| active | ✅ `liveGoal()` returns the state |
| paused | ✅ `liveGoal()` returns the state |
| achieved | ✅ `liveGoal()` returns null, `shouldShowCreateForm()` returns true |
| **stalled** | ❌ No type, no detection, no UI |
| stopped/cleared | ✅ `liveGoal()` returns null, `shouldShowCreateForm()` returns true |

A goal run that hangs — agent stopped responding, network partition, provider timeout, sidecar crash — has no representation in the dock. It stays "active" indefinitely (confusing) or eventually hits a constraint and becomes "cleared" (misleading about cause).

**What's needed:**
- Plugin: detection logic (no-turn-in-N-minutes heuristic, or session-idle-without-progress signal)
- Plugin: `status: "stalled"` in the goal state schema
- App: `"stalled"` case in `statusMeta()`, `STATUS_META`, `nodeColor()`, and the lifecycle model
- App: stalled goals render with a distinct visual treatment (amber/warning, distinct from active green)

## Gap 3 — Attention Detection: Missing Limit-Hit and Stalled Cases

**Severity:** Feature gap
**Surface:** Home page (`buildHomeAttentionRecords`)
**Testable?** Yes

The spec (lines 96-103):

> A secondary status area for important interrupts, including:
> - runs that hit turn limits
> - runs that hit time limits
> - failed or stalled jobs
> - work waiting for input

`buildHomeAttentionRecords` (home.tsx:244-386) detects:

| Spec Case | Detected? | How |
|---|---|---|
| Permission requests | ✅ | `sessionPermissionRequest()` |
| Questions waiting | ✅ | `sessionQuestionRequest()` |
| Retry status | ✅ | `status?.type === "retry"` |
| Session errors | ✅ | Unseen error notifications |
| Unread updates | ✅ | Unseen response notifications |
| Orphan project alerts | ✅ | Project-level unseen notifications |
| **Turn limit hit** | ❌ | Not detected |
| **Time limit hit** | ❌ | Not detected |
| **Failed/stalled jobs** | ❌ | Not detected |

Goal runs that exhausted their budget are invisible on the home page. The budget enforcement works (the plugin stops the run and sets `status: "cleared"`), but the home page never surfaces *why* a run stopped. A user with 5 projects and 3 active goals has to open each session to discover which ones hit limits.

**What's needed:**
- Plugin: expose stop-reason in a machine-readable field (currently only in `lastEvaluation.reason` as a human string)
- App: read stop-reason from goal state or archive, surface as an attention record
- App: distinct attention `kind` for limit-hit (e.g., `"goal-limit"`) with appropriate priority

## Gap 4 — Token Budget: Read-Only Despite Adjacent Inline Editing

**Severity:** Partial implementation
**Surface:** Goal dock
**Testable?** Yes

The spec's budget section (lines 191-212):

> Both budgets must be editable inline via small stepper controls: `-` decrease, `+` increase
> turns cap and time cap are both visible at all times

The implementation has `BudgetDial` with `-`/`+` steppers for **Turns** (`constraints.maxTurns`) and **Time** (`constraints.maxTimeMinutes`). The **Token** budget appears in the constraints utility zone (goal-panel.tsx:1587-1603) as static read-only numbers:

```
Max tokens    100000
Used tokens   12,450
```

No steppers. No editing. Token caps cannot be adjusted from the dock — only via `/goal tokens <n>` in chat.

**Nuance:** The spec's budget row description names only Turns and Time. Tokens appear separately in the constraints/utility zone section. Whether tokens *should* be inline-editable depends on interpretation, but the user cannot adjust token caps from the GUI, which creates an asymmetry: two of three hard-stop conditions are GUI-editable, one is chat-only.

## Gap 5 — Responsive Behavior: No Narrow/Medium Verification

**Severity:** Test gap
**Surface:** All three surfaces
**Testable?** Partially — CSS class assertions can verify structure; actual rendering needs browser/Electron

The spec (lines 163-167, 259-265):

> Wide: conversation center + right dock
> Medium: same shape, with tighter secondary rows
> Narrow: stack support surfaces intelligently while preserving center-surface importance
> Narrow: utility zone stacks vertically while status band and command strip remain intact

Zero tests exercise viewport width. CSS classes exist (flex-wrap, stacking, responsive grid), but there's no programmatic proof that:

- Utility zone goes single-column below the narrow breakpoint
- Status band and command strip remain intact (don't stack or hide)
- History pills tighten at medium width
- The left sidebar collapses or transforms at narrow widths

This gap is inherent to headless SolidJS testing — there's no DOM layout engine to compute flex-wrap behavior. It needs either:
- A browser-based test (Playwright, happydom with layout simulation)
- Manual verification in the Electron window at each breakpoint
- Screenshot diff testing for regression detection

## Gap 7 — No End-to-End Integration Test (GUI Walkthrough)

**Severity:** Test gap
**Surface:** Full flow
**Testable?** Yes — needs SDK mocking

Every component is individually tested (552 app tests), but no test walks the full user flow:

> Home page → new session → `/goal set "fix all tests" --command "npm test"` → dock populates with status/progress/budget → click `-` on turns → click Pause → click Resume → run completes → Stop → history drawer opens with completed run → click history pill → detail shows stats → navigate back to home → see run in recent sessions

This is the flow that breaks when the *wiring* between components is wrong but each component is individually correct. The OpenGoal repo has `test/walkthrough-v070.test.mjs` for the standalone TUI control center. The app repo has no equivalent.

**What's needed:** A test file that:
1. Mocks the SDK client (file.read, session.command, session.prompt)
2. Renders the goal panel (or the full session shell)
3. Simulates each user action in sequence
4. Asserts the post-condition at each step
5. Runs under `bun test --preload ./happydom.ts`

## Gap 8 — Feature Flag Gate: New UI Is Opt-In on Prod

**Severity:** Risk
**Surface:** Entire new UI
**Testable?** Yes

`home.tsx:396`:
```tsx
<Show when={settings.general.newLayoutDesigns()} fallback={<LegacyHome />}>
```

The entire mission-control UI — home page, goal dock, V2 session header, new layout, V2 titlebar — is behind `settings.general.newLayoutDesigns`. The default is:

```ts
// settings.tsx:55
export const newLayoutDesignsDefault = import.meta.env.VITE_OPENCODE_CHANNEL !== "prod"
```

So dev builds see it; prod builds don't. Verification gaps:

- **No test verifies the legacy fallback still works.** If a refactor to `HomeDesign` accidentally broke `LegacyHome`, no test catches it.
- **No test verifies the toggle transition.** Toggling the setting on/off should not lose state, crash, or leave the UI in an inconsistent mode.
- **Prod users won't see this work** unless they discover the setting in General preferences. The setting has a label and description in all three locale files, but it's not discoverable without reading release notes.

## Gap 9 — Visual/Aesthetic Requirements: Headless by Construction

**Severity:** Inherent
**Surface:** All surfaces
**Testable?** No — needs Electron screenshots

These spec requirements have **no programmatic verification** with the current test infrastructure (SolidJS + happydom + bun test — no layout engine, no paint, no compositing):

| Spec Line | Requirement | Verifiable? |
|---|---|---|
| 13 | "stronger hierarchy" | Visual only |
| 14 | "less sparse and plain layout" | Visual only |
| 15 | "clearer action exposure" | Partially — button presence is testable; visual prominence is not |
| 107-112 | "denser cards, stronger borders, clearer grouping" | Visual only |
| 130-133 | "stronger contrast, clearer content grouping, better visual rhythm" | Visual only |
| 227-230 | "better outlines, clearer grouping, stronger hover/focus states" | Hover/focus states partially testable via CSS class assertions; visual quality is not |
| 313-317 | "charcoal/muted dark panels, sharper borders, restrained saturated color" | Visual only |
| 330-334 | "stronger outlines on cards/pills/controls, more obvious container boundaries" | Visual only |

The 30+ Electron screenshots in `OpenGoal/` (e.g., `electron-home-final-counters-attention-goals.png`, `electron-session-goal-collapsed.png`) suggest Director Gabriel has been doing visual verification manually. This is the correct approach for now — headless tests cannot replace eyes on the Electron window.

**Future enhancement:** Screenshot diff testing (take a screenshot, compare against a known-good baseline) would catch visual regressions. But this requires the Electron window to be running, which is a different test infrastructure than the current `bun test` suite.

## Gap 10 — "Work Waiting for Input": Partially Implemented

**Severity:** Partial implementation
**Surface:** Home page
**Testable?** Yes

The attention builder catches permission requests and questions — both are forms of "waiting for input." But:

- **Goal runs that need steering** (the user paused to give guidance, or the agent asked a clarifying question mid-run) don't surface as attention items.
- **Goal runs that are "active" but haven't had a turn in 10+ minutes** (stalled/dead) have no attention signal — this overlaps with Gap 2 and Gap 3.
- **Agent errors that require human intervention** (provider auth failure, tool permission denied) are surfaced as session errors but not distinguished from transient errors.
